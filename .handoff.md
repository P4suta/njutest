# Handoff — the Windows half, and one proposal it did not land

Written from the Windows box on 2026-09-23, against `work/win/campaign`.

## Proposal, not on this branch: make a checkpoint take nearly free

This is a design change to the step protocol. It is recorded here rather than
written, because this branch is trying to land.

### What it would fix

Deciding "this mutant does not terminate" has two stoppers: the step count and
the wall-clock bound. The count is a property of the program and is the same
number on every machine. Which stopper *arrives first* is not, so the verdict
is machine-dependent, and a slow enough machine reports a proved
non-termination as a mere `waited` with no notice. ADR 0023 already forbids
concluding from an artifact of how a run measured; this is one.

### Why it is a race today

`checkpoint()` calls `update_state` in `crates/rust-mutants/src/instrument/runtime.rs`,
and that does a full locked durable round trip per boundary crossing: read
three environment variables, open the state file, `lock()`, read metadata, read
the state, compute the transition, write, `sync_data()`, close.

Measured on this box: **7.3ms per take**, plus about 55ms of process start.
A hundred takes cost 789ms of a two-second bound. On a CI runner with slower
storage the rest of that bound went too, which is how the Windows job reported
`outcome=waited`, `step_notice=null`, `retried=true`, `duration_ms=4052` — two
attempts of a two-second bound — for the mutation that deletes `step += 1;`.

### The change

Keep the state file as the owner of the total, so a single allowance still
spans a process tree. Make the fast path a lease:

- a process reserves a block of `K` takes from the file in one round trip
- it spends them against an in-process atomic
- it returns to the file when the block is exhausted, and when the allowance is
  crossed, which is the existing notice and stays exact

Cost per take becomes `7.3ms / K` plus an atomic increment. At `K = 1024` that
is about 7µs, roughly a thousandfold, and an allowance of ten is reached in
well under a millisecond on any machine. The race stops being one.

### What it changes and what it does not

No verdict changes. The allowance is still the same count, the boundary is
still `N + 1`, and the notice at the boundary is still written before the
process parks.

The one semantic change is granularity under a kill: a process killed mid-block
loses up to `K` takes of *published progress*. The notice is unaffected, so
nothing that decides an outcome is lost.

### How it would be verified

The invariants are already pinned by `crates/rust-mutants/tests/touch_runtime.rs`:
one allowance spans file modules, repeated guard checks do not spend twice, and
a closure reentered by an external iterator spends the global allowance. Those
become the acceptance suite unchanged.

One test is missing and should be written first: a child killed mid-block
publishes progress within `K` of its true count.

The cost claim is checkable by rerunning the measurement this proposal is built
on — a hundred takes should cost about what one take costs now.

### After it, two smaller things become possible

1. **Tell "not computing" from "slow".** Once a take is free, a `waited` means
   the process raised no count at all, which is a process that was asleep or
   blocked rather than spinning. The count at the moment of the kill is the
   evidence, and ADR 0023's second way out is to capture it rather than infer.

2. **Take the clock out of the verdict.** The bound becomes a safety net that
   ends a process rather than a thing that decides about one, and
   `[mutation] timeout` can default generously without making a failing suite
   slow to read — which is the objection that rules out simply lengthening it
   today.

### What it would still not reach

A mutation that is slower but terminating is the clock's, and must be: no count
separates slow from very slow. Code the instrumenter does not rewrite — macro
expansions, dependency crates, FFI — raises no count, and that is the gap
`docs/limitations.md` now describes. `Inconclusive` is unchanged.

## Corrected on this branch: what the count already reaches

`docs/limitations.md` said a guard sits only where its mutation does, so a
mutation *outside* a loop that makes the loop spin was taken once and could
only be stopped by the clock. That is no longer true, and the correction is on
this branch.

`crates/rust-mutants/src/instrument/mod.rs` places control-flow checkpoints in
every mutable file, including one with no mutant of its own. Two throwaway
workspaces written to check it both report `step_limit_reached` at `N + 1` with
`waited=0`: one with the literal and the loop in the same file, one with the
loop in a second file the run is not mutating. The document was describing the
instrumenter as it was before checkpoints were placed across a workspace.

**This wants a fixture and does not have one.** The correction rests on a
measurement nothing in the tree repeats, which is the shape of claim this
repository otherwise refuses. A `fixture-outside` of the second shape — the
literal in one file, the loop in another, no mutant in the second — and a
toolchain test asserting `step_limit_reached` for the literal would pin it.
It was left out of this branch because a new fixture moves the mutant counts
several suites assert on, and this branch is trying to land.

## The Windows state this branch leaves

`test:fast` 2056/2056. `test:slow` 352 of 437, the rest behind `cfg(unix)`
because report publication is rooted at a POSIX directory capability and
answers `NJ6004` here, which `docs/limitations.md` already recorded.

Fourteen tests in those suites do not need a published report — the refusals,
`plan`, the stream split, the watch verdict — and are gated per test rather
than per file so Windows keeps them. They are where this platform's path
handling differs, so they are the ones most likely to catch the next defect.

Windows-only Clippy is not answered: 29 denials behind `cfg(windows)`, mostly
the `cfg(not(unix))` store stubs in `crates/njutest/src/app/reports.rs`. CI does
not read them — the Windows job runs tests and doctests, and `lint` runs on
Ubuntu — but `mise run lint` cannot pass on this box until they are.

`committed` fails on six commits that predate this work, all PR-squash subjects
over 72 characters plus one non-imperative. They are not this branch's to
rewrite, but `origin/main..HEAD` is what the lint job checks.
